Rule Engine POC — Rules & Routing

Library tables, how they link, and which rule lives where.

Planned design — library v3.0.0, not implemented yet. This page shows the target schema so it can be reviewed before any code changes. Flows and groups become real rows with ids, and every rule belongs to exactly one group.
Why the change

Today (v2) — a rule points at a group name

RULE_DEFINITION rule_name = "Block high-value cross-border…" UNIQUE agenda_group = "COMPLIANCE" ← just a string Transfer › COMPLIANCE ─┐ ├─ same bucket, same rules Closure › COMPLIANCE ─┘
  • Both COMPLIANCE screens list the same rules.
  • Editing a rule from one flow changes it in the other — it's one row.
  • A rule name can exist only once in the whole system.

Planned (v3) — a rule points at a group id

RULE_GROUP id=4 TRANSFER_TRANSACTION.COMPLIANCE RULE_GROUP id=7 ACCOUNT_CLOSURE.COMPLIANCE RULE_DEFINITION group_id = 4 ← FK to one exact group rule_name UNIQUE per group only
  • Each flow's COMPLIANCE is its own row with its own rules.
  • The same rule name may exist in both groups.
  • COMMON is one shared group, so blocked-user / KYC exist once.
Database design

Four tables, joined by real foreign keys. RULE_FLOW is the flow master and the router — routing is 1:1 (one request_class → one flow), so the request class is a UNIQUE column here, not a separate mapping table. group_id and flow_id are FKs to RULE_FLOW. A dashed arrow is a nullable FK: NULL there = shared by every flow (the COMMON group and its shared fields). request_class and fact_type live once, on RULE_FLOW. Every flow, group and rule carries an active flag (on/off), and each rule keeps both its editable source_json and the generated drl_text.

foreign key (many → one) nullable FK — NULL = shared PK primary key UQ unique constraint
Flow → stages → group → rules

What each flow runs, top to bottom. The two COMPLIANCE groups are outlined: same name, different ids, different rules. COMMON (dashed) is the same group #1 in every flow.

At runtime

execute(context, LoanRequest.class, globalContext) → request type picks the flow → the flow's stages give the agenda keys to focus, in order. Both flows' COMPLIANCE rules share the COMPLIANCE Drools bucket, but a transfer only ever inserts a transfer fact, so closure rules never fire there. In the database they are still two separate group rows (#4 vs #7).

Tables & rows
Now allowed — same name in two groups. UNIQUE(group_id, rule_name) lets a rule called, say, "Block high-value cross-border non-BDT transfer" exist in group #4 and again in group #7. They are two rows with two ids; editing one never touches the other. The compiled DRL name is prefixed with the agenda key (TRANSFER_TRANSACTION.COMPLIANCE::…), so Drools still sees unique names.
drl_text & source_json — every rule

Builder rules show both the editable JSON and the DRL generated from it. Hand-written DRL rules (COMMON) have no JSON.

Admin API (planned)
MethodPathPurpose
Delete vs. active/inactive — two separate actions. Every flow, group and rule has an active flag (the UI on/off radio) and a delete. Deactivate keeps the row but skips it when a business request hits: an inactive rule is not compiled, an inactive group is not focused, and an inactive flow runs nothing at all. Delete removes the row for good (?force=true cascades to children). So a screen can be switched off without losing its rules, then switched back on.
Consumer API is unchanged. Services still call ruleExecutionService.execute(context, TransactionRequest.class, globalContext). Flows themselves stay developer-managed (DB seed); end users manage groups and rules.
