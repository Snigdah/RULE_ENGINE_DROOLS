Preface. About this guide

This guide is for developers who add com.leads:rule-engine to a business microservice. It does not cover building rules in the Rule Builder UI; rule administrators do that.

Every example uses the same scenario: a fund transfer service that must block a transfer when the amount is over the user's limit on a debit-restricted account. Follow the chapters in order to go from an empty service to running rules.

Chapter 1. Overview

The library runs business rules stored in the database. Rules can be added, changed, switched on and off, or deleted at runtime, without redeploying your service.

1.1. Key concepts

Flow RULE_FLOW

One business operation, such as TRANSFER_TRANSACTION. Each request class maps to exactly one flow.

Rule group RULE_GROUP

An ordered stage inside a flow, such as TRANSFER then COMPLIANCE. Groups fire top to bottom.

Rule RULE_DEFINITION

One condition and its outcome (block or allow). Built in the Rule Builder and stored as JSON plus generated DRL.

Field catalog RULE_FIELD_CATALOG

The fields rule authors can pick, each mapped to a real property path on your context object.

Context

A Java object your service fills with request data and looked-up data. Rules read it and write the decision back into it.

Root

The first part of a field path. userLimit.limit has root userLimit. One lookup fills one root.

1.2. How a request runs

When your service receives a request, five things happen. Only the lookups your service performs touch the database; everything the library does at request time is in memory.

01
Request arrives
Your controller receives a TransactionRequest.
02
Ask what is needed
requiredData() returns the roots the active rules read.
03
Load data
Your service runs only the needed lookups.
04
Run rules
execute() fires the flow's groups in order.
05
Read decision
Your service reads valid and the message.
In memory, no database callYour database or service calls

1.3. What is cached

ItemWhere it lives at request timeDatabase call per request
Compiled rulesIn memory, rebuilt when rules changeNo
Routing (request class → flow → groups)In memory, rebuilt when flows or groups changeNo
Required data (roots per flow)In memory, rebuilt with the rulesNo
Business data (user limit, product, …)Loaded by your serviceYes, only what is needed

Chapter 2. Installing the library

The library is a Spring Boot starter. Add the dependency and the four tables; everything else registers itself.

Prerequisites

  • Spring Boot 3.5.x and Java 21.
  • Access to the internal Nexus repository that hosts com.leads:rule-engine.
  • A database where your service can create four tables (Oracle or PostgreSQL).

Procedure

  1. Add the dependency to pom.xml.

    xmlpom.xml
    <dependency>
    <groupId>com.leads</groupId>
    <artifactId>rule-engine</artifactId>
    <version>3.0.3</version>
</dependency>

  2. Create the four library tables: RULE_FLOW, RULE_GROUP, RULE_DEFINITION and RULE_FIELD_CATALOG. Whether you run a script depends on spring.jpa.hibernate.ddl-auto; see 2.1. Database schema.

  3. Add the library settings to application.yml.

    yamlapplication.yml
    rule-engine:
  admin:
    enabled: true            # expose the /admin API (default true)
  required-data:
    enabled: true            # load only the data active rules need (default false)
    shadow: false            # true = log what would be skipped, but load everything
    trust-drl-hints: true    # read "// @requires:" lines in hand-written DRL
!
Important

The rule-engine block is optional. If you leave it out, the service still runs every rule correctly, using the defaults: the admin API stays on, and required-data.enabled is false. With that default, need.needs(...) always answers true, so every lookup runs as before. You only lose the saving from skipped lookups. See 5.4. Safety rules.

Table 2.1. What changes when the block is missing

SettingWithout the blockEffect on your service
admin.enabledtrueAdmin API available
required-data.enabledfalseRules run normally; needs() is always true, no lookups skipped
required-data.shadowfalseNo effect while the feature is off
required-data.trust-drl-hintstrueNo effect while the feature is off

Verification

Start the service and call GET /admin/flows. An empty list [] means the library is running and the tables are reachable.

i
Note

The library uses its own package, leads.ruleengine.core, for its entities, repositories and controllers. It does not scan or touch your own packages.

2.1. Database schema

The library's entities map to four tables. Who creates them depends on the spring.jpa.hibernate.ddl-auto setting of your service.

Table 2.2. Who creates the library tables

!
Important

In a banking or production database, keep ddl-auto at none or validate and have the DBA run the script below once per service schema, before the service starts for the first time. The script is also shipped inside the library jar at db/oracle/schema-oracle.sql.

Procedure

  1. Connect to the schema the service uses, as a user that can create tables, sequences and indexes.

  2. Run the script below as one migration. The statements are already in foreign-key order: RULE_FLOW, then RULE_GROUP, then RULE_DEFINITION and RULE_FIELD_CATALOG.

  3. Run your seed script for flows, groups and catalog fields (see 3.2. Register the flow), then start the service.

Chapter 3. Onboarding a request type

To run rules for a new business operation, write two Java classes and register them with the library once. After that, rule authors manage the rules themselves.

3.1. Write the request and context classes

The request class is what your API receives; its full class name selects the flow. The context class holds only the data the rules read. It needs no decision fields: the library returns the decision separately (see 4.2. Reading the decision).

javaValidationContext.java
public class ValidationContext {

    // data the rules read (each one is a root)
    private String userId;
    private Transaction transaction;   // built from the request
    private UserLimit userLimit;       // looked up
    private Product product;           // looked up
    private User user;                 // looked up

    // getters and setters for every field - no decision fields needed
}
i
Note

Earlier versions required valid, permissionDenied and validationMessage on every context. They are no longer needed. A context that still has them keeps working: the library copies the decision onto it as well.

3.2. Register the flow

Register the flow once through the admin API. requestClass and factType are full class names.

Procedure

  1. Create the flow and its ordered groups.

    bash
    curl -X POST http://localhost:8080/admin/flows \
  -H "Content-Type: application/json" -d '{
    "flowCode":     "TRANSFER_TRANSACTION",
    "requestClass": "com.leads.transfer.dto.TransactionRequest",
    "factType":     "com.leads.transfer.model.ValidationContext",
    "label":        "Transfer Transaction",
    "groups":       ["TRANSFER", "VELOCITY", "COMPLIANCE"]
  }'

  2. Add the fields rule authors may use. drlPath is the real property path on your context; use !. after any object that can be null.

    bash
    curl -X POST http://localhost:8080/admin/fields \
  -H "Content-Type: application/json" -d '{
    "flowCode":   "TRANSFER_TRANSACTION",
    "fieldKey":   "userLimit.limit",
    "label":      "User Limit",
    "dataType":   "NUMBER",
    "drlPath":    "userLimit!.limit",
    "allowedOps": "> < >= <= == !="
  }'

    Repeat for each field, for example transaction.amount, transaction.currency and product.drRes. Leave flowCode out to share a field with every flow.

    !
    Important

    The field catalog has no UI. In development you can add fields with the API call above. For a client deployment, catalog rows are delivered as a database migration script that runs with the release, so every environment gets the same fields.

    sqlV3_0_2__transfer_field_catalog.sql (PostgreSQL)

VALUES
  (nextval('rule_field_catalog_seq'),
   (SELECT id FROM rule_flow WHERE flow_code = 'TRANSFER_TRANSACTION'),
   'userLimit.limit', 'User Limit', 'NUMBER', 'userLimit!.limit',

    sqlV3_0_2__transfer_field_catalog.sql (Oracle)
    INSERT INTO RULE_FIELD_CATALOG
  (ID, FLOW_ID, FIELD_KEY, LABEL, DATA_TYPE, DRL_PATH, ALLOWED_OPS, ALLOWED_VALUES)
VALUES
  (RULE_FIELD_CATALOG_SEQ.NEXTVAL,
   (SELECT ID FROM RULE_FLOW WHERE FLOW_CODE = 'TRANSFER_TRANSACTION'),
   'userLimit.limit', 'User Limit', 'NUMBER', 'userLimit!.limit',
   '> < >= <= == !=', NULL);

    Run the script before the service starts, or call POST /admin/flows/reload afterwards so the running service picks up the new fields. Use NULL for flow_id to share a field with every flow.

Verification

GET /admin/flows/TRANSFER_TRANSACTION/groups lists the three groups in order, and GET /admin/flows/TRANSFER_TRANSACTION/fields lists your fields.

3.3. What rule authors do next

Administrators build rules in the Rule Builder UI, or post them to POST /admin/groups/{groupId}/rules. Each builder rule is saved as a JSON condition tree; the library turns it into DRL and compiles it before saving. A rule that does not compile is rejected and never reaches the running engine.

jsoncondition tree of one builder rule
{
  "type": "GROUP", "operator": "AND",
  "children": [
    { "type": "CONDITION", "field": "transaction.currency", "operator": "==", "value": "BDT" },
    { "type": "CONDITION", "field": "product.drRes",        "operator": "==", "value": 1 },
    { "type": "CONDITION", "field": "transaction.amount",   "operator": ">",  "valueField": "userLimit.limit" }
  ]
}

Chapter 4. Running the rules and reading the result

Inject RuleExecutionService, fill a context, and call execute with your request class. The request class picks the flow, the context is what the rules read, and the returned RuleResult is the decision.

javaTransactionRuleService.java
@Service
public class TransactionRuleService {

    private final RuleExecutionService ruleEngine;

    public TransactionResponse validate(TransactionRequest request) {
        ValidationContext context = buildContext(request);           // chapter 5

        RuleResult result = ruleEngine.execute(context, TransactionRequest.class);

        return new TransactionResponse(
                result.isValid(),
                result.isPermissionDenied(),
                result.getMessage());
    }
}

4.1. The two forms of execute

CallUse when
RuleResult execute(context, X.class)All rules are builder rules. This is the normal case.
RuleResult execute(context, X.class, globalContext)A hand-written DRL rule reads shared reference data through the globalContext global.
i
Note

Builder rules never use the global context, so passing it or not makes no difference to them.

4.2. Reading the decision

Every call returns a new leads.ruleengine.core.context.RuleResult. It starts as valid; a rule with the outcome block marks it blocked and sets its message. If no rule matches, the request passes.

Table 4.2. RuleResult methods

MethodReturns
isValid()true unless a rule blocked the request
isPermissionDenied()true when a rule blocked the request
getMessage()The message of the deciding rule, or null
isDecided()true when any rule made a block or allow decision

Builder rules write to it through a Drools global named result. This is the generated then part of a blocking rule:

drlgenerated by the library
global leads.ruleengine.core.context.RuleResult result;

rule "TRANSFER_TRANSACTION.TRANSFER::Block over-limit debit-restricted BDT transaction"
    when
        $ctx : ValidationContext( transaction.amount > userLimit!.limit, ... )
    then
        result.block("Blocked: amount exceeds limit on a debit-restricted BDT account");
end
✓
Tip

A hand-written DRL rule can use the same object: declare global leads.ruleengine.core.context.RuleResult result; and call result.block("…") or result.allow("…").

Requestvalidmessage
BDT 5,000 from a normal accounttrue(none)
BDT 20,000 from a debit-restricted account, limit 10,000falseBlocked: amount exceeds limit on a debit-restricted BDT account
✓
Tip

A flow that is switched off runs no rules, so every request passes. This is intentional and is not an error.

4.3. How several rules combine

Every rule that matches writes to the same RuleResult. Rules run group by group in the flow's order; inside a group, a higher salience runs first.

  • result.block(msg) sets valid = false and permissionDenied = true.
  • result.allow(msg) sets valid = true. It does not clear permissionDenied.
  • A non-blank message replaces the previous one, so the last rule that set a message provides it.
  • If no rule matches, the result stays valid = true, permissionDenied = false, message null, and isDecided() is false.

Table 4.3. Worked example: transfer of USD 150,000 to country OTHER

OrderGroupRuleMatchesResult after the rule
1TRANSFERHigh-value or cross-border transferyesvalid = false · "Blocked: high-value agent transfer, or cross-border non-BDT transfer"
2VELOCITYBlock rapid high-value agent transfersnounchanged
3COMPLIANCEBlock high-value cross-border non-BDT transferyesvalid = false · "Blocked: cross-border high-value transfer needs manual review"

The service receives valid = false with the COMPLIANCE message, because that rule wrote last.

✓
Tip

Put the group whose message the customer should see last in the flow's order, or give its rules a lower salience within the same group.

4.4. Using the result in your service

Return it to the caller, turn a block into an error, or log it. These are the common patterns.

javamap to the API response
RuleResult result = ruleEngine.execute(context, TransactionRequest.class);
return new TransactionResponse(result.isValid(), result.isPermissionDenied(), result.getMessage());
javastop the business operation on a block
RuleResult result = ruleEngine.execute(context, TransactionRequest.class);
if (!result.isValid()) {
    throw new ResponseStatusException(HttpStatus.UNPROCESSABLE_ENTITY, result.getMessage());
}
transferService.post(request);   // only reached when no rule blocked
javaaudit log
log.info("rules {} user={} -> {}", "TRANSFER_TRANSACTION", request.getUserId(), result);
// rules TRANSFER_TRANSACTION user=USER-001 -> RuleResult{valid=false, permissionDenied=true, message='...'}
i
Note

Each call to execute returns a new RuleResult. It is safe to keep, log or pass on; it is never shared between requests.

4.5. Writing the result from hand-written DRL

Builder rules use RuleResult automatically. A hand-written DRL rule declares the global once and calls the same methods.

drlhand-written rule
package com.leads.transfer.rules;

import com.leads.transfer.model.ValidationContext;

global leads.ruleengine.core.context.RuleResult result;

rule "Block weekend agent transfers over 1,00,000"
    agenda-group "TRANSFER"
    when
        $ctx : ValidationContext( transaction.channel == "AGENT", transaction.amount > 100000 )
    then
        result.block("Blocked: agent limit exceeded");
end

4.6. Migrating from context decision fields

Before 3.0.2, every context carried valid, permissionDenied and validationMessage, and the service read them after execute. Move to the returned result as follows.

Table 4.4. Before and after

Before (3.0.1 and earlier)From 3.0.2
ruleEngine.execute(context, X.class);RuleResult result = ruleEngine.execute(context, X.class);
context.isValid()result.isValid()
context.isPermissionDenied()result.isPermissionDenied()
context.getValidationMessage()result.getMessage()
Three decision fields on every contextRemove them
DRL: $ctx.setValid(false); $ctx.setPermissionDenied(true);DRL: result.block("…");

Procedure

  1. Change the dependency to 3.0.3 and rebuild.

  2. Read the decision from the returned RuleResult instead of the context.

  3. Remove the three decision fields from your context classes.

  4. Update any hand-written DRL that calls $ctx.setValid(…) to use the result global (section 4.5).

  5. Start the service. Builder rules are upgraded automatically.

Verification

The startup log shows Upgraded N builder rule(s) to write the library RuleResult. on the first start, and GET /admin/rules/{id} shows result.block(…) in drlText.

!
Important

You can upgrade in steps. A context that still has the three setters also receives the decision, so code that reads context.isValid() keeps working until you switch it to RuleResult. Do not remove the fields while hand-written DRL still writes to them.

Chapter 5. Loading only the data you need

Each lookup costs a database or service call on every request. If no active rule reads a piece of data, there is no reason to load it. The library tells you which data the active rules read, so you can skip the rest.

5.1. Ask, then check before each lookup

Call requiredData once per request. It is answered from memory. Then put need.needs("root") in front of each lookup.

javaTransactionRuleService.java
import static java.util.concurrent.CompletableFuture.completedFuture;
import static java.util.concurrent.CompletableFuture.supplyAsync;

private ValidationContext buildContext(TransactionRequest request) {
    RequiredData need = ruleEngine.requiredData(TransactionRequest.class);   // memory, no DB

    // same parallel code as before - each lookup now has a needs() check in front
    CompletableFuture<UserLimit> limitF = need.needs("userLimit")
            ? supplyAsync(() -> lookup.userLimit(request.getUserId()), lookupExecutor)
            : completedFuture(null);

    CompletableFuture<Product> productF = need.needs("product")
            ? supplyAsync(() -> lookup.product(request.getSourceAccount()), lookupExecutor)
            : completedFuture(null);

    CompletableFuture<User> userF = need.needs("user")
            ? supplyAsync(() -> lookup.user(request.getUserId()), lookupExecutor)
            : completedFuture(null);

    CompletableFuture.allOf(limitF, productF, userF).join();

    ValidationContext context = new ValidationContext();
    context.setUserId(request.getUserId());       // from the request - always set
    context.setTransaction(toFact(request));      // from the request - always set
    context.setUserLimit(limitF.join());          // null when no active rule reads it
    context.setProduct(productF.join());
    context.setUser(userF.join());
    return context;
}

Without parallel lookups, it is a plain if. The data can come from a repository, another service, or a cache; the library only answers yes or no.

javasequential form
if (need.needs("userLimit")) {
    context.setUserLimit(userLimitRepository.findByUserId(request.getUserId()));
}

5.2. Which name to pass

Pass the root: the first part of the field's drlPath in the catalog. One lookup fills one root, so one lookup gets one check.

Catalog drlPathRoot to passLookup it guards
userLimit!.limit"userLimit"lookup.userLimit(...)
product!.drRes"product"lookup.product(...)
user!.kycVerified"user"lookup.user(...)
transaction.currency(no check)Built from the request, so it is free
!
Warning

Do not pass a field such as "transaction.currency", and do not guard one lookup with another root's name. The check must name the data that lookup loads.

5.3. How the library works out the roots

The answer is computed once, when rules reload, and kept in memory. It follows four steps.

  1. Find the rules that can fire. Active rules in the flow's active groups, plus active shared groups.

  2. Read every condition of each builder rule, however deeply nested, taking both field and valueField.

  3. Turn each field into its root using the catalog drlPath: userLimit.limit → userLimit!.limit → userLimit.

  4. Remove duplicates. The result is roots.

You can see the result for any flow:

httpGET /admin/flows/TRANSFER_TRANSACTION/required-data
{
  "flowCode":   "TRANSFER_TRANSACTION",
  "roots":      ["userLimit", "product", "transaction"],
  "fields":     ["transaction.amount", "userLimit.limit", "transaction.currency",
                 "transaction.country", "transaction.dailyTxnCount",
                 "transaction.channel", "product.drRes"],
  "knownRoots": ["userLimit", "user", "transaction", "product"],
  "complete":   true
}
PartMeaningUsed by needs()
rootsObjects the active rules read. These must be loaded.Yes, this is the answer
knownRootsEvery root the flow could have, from its catalog.Only to catch typos
fieldsThe exact fields the active rules read.No, for reading only
completetrue when every active rule could be checked.Yes: false loads everything

With this response, the three checks give:

CallResultWhy
needs("userLimit")trueIn roots; the over-limit rule reads userLimit.limit.
needs("product")trueIn roots.
needs("user")falseNo active rule reads user. The lookup is skipped.
needs("userLimt")trueNot a known root (typo). Logs an ERROR and loads, to stay safe.

5.4. Safety rules

  • needs() answers false only when it is proven that no active rule reads that root.
  • When the feature is off (required-data.enabled: false) or in shadow mode, needs() always answers true.
  • A hand-written DRL rule without a // @requires: line cannot be checked, so its whole flow loads everything (complete: false).
  • A service that never calls requiredData() keeps working exactly as before.
✓
Tip

Roll out with shadow: true first. The service still loads everything, and the debug log shows what it would have skipped. Switch shadow off once the log matches your expectation.

Chapter 6. Designing the context object

Rules reach your data only through the context's getters, following each field's drlPath. A few simple habits keep rules reliable.

6.1. Rules for the context

  • Give every path a public getter. userLimit.limit needs getUserLimit() on the context and getLimit() on UserLimit.
  • Nesting works to any depth. userLimit!.policy!.tier is valid; the root is still userLimit.
  • Use !. after anything that can be null. A skipped lookup leaves its root null. With !. the condition is simply false instead of failing.
  • Fields directly on the context are roots too. A field userName has root userName.
  • Collections need hand-written DRL. The builder compares single values, not lists.

6.2. Example: nested path

textcatalog row → generated DRL
fieldKey : userLimit.policy.tier
drlPath  : userLimit!.policy!.tier

generated: $ctx : ValidationContext( userLimit!.policy!.tier == "GOLD" )
root     : userLimit
!
Warning

If you rename a getter, update the catalog drlPath and re-save the affected rules. Otherwise the rules no longer compile on the next reload.

Chapter 7. Runtime changes and caching

Rules, routing and required data live in memory. Changes made through the admin API refresh all three at once; you do not call any reload endpoint.

7.1. What happens on a rule save

  1. Compile check. The new rule set is compiled in a throw-away container. A rule with errors is rejected with HTTP 400 and nothing changes.

  2. Save. The rule is written to RULE_DEFINITION.

  3. Required data first. Roots and fields are recomputed, so the new rule's data is loaded before the rule can run.

  4. Rules second. The freshly compiled rules replace the old ones in one atomic swap. Requests in progress finish on the old rules.

Admin changeRefreshes automatically
Rule create, update, delete, on/offCompiled rules and required data
Group or flow add, delete, reorder, on/offRouting and required data
Catalog field add or deleteRequired data
i
Note

At startup, builder rules saved by an older library version (which wrote $ctx.setValid(…)) are regenerated automatically from their stored JSON to write RuleResult. Hand-written DRL rules are never changed.

7.2. Direct database changes

If someone changes the tables with SQL, the service does not notice until something reloads.

Changed with SQLWhat to do
Flow or group (active, order)POST /admin/flows/reload
Field catalogPOST /admin/flows/reload
A rule in RULE_DEFINITIONRestart the service, or call PUT /admin/rules/{id}/active on any rule
!
Warning

Never edit source_json directly in the database. The engine runs drl_text, which is only regenerated by PUT /admin/rules/{id}. If they differ, the required-data analysis reads the new conditions while the engine runs the old ones, and a rule can run without its data.

Appendix C. Glossary

A rule made in the Rule Builder and stored as a JSON condition tree. The library generates its DRL.
DRL rule
A hand-written Drools rule. It may declare what it reads with // @requires: root, ….
Fact type
The full class name of the context object a flow's rules match.
Root
The first part of a drlPath. The unit a service loads with one lookup.
RuleResult
The decision returned by execute(): valid, permission denied and message. Rules write it through the result global.
Firing set
The active rules in a flow's active groups plus active shared groups.
Shared group
A group with no owning flow; it fires first in every flow.
Complete
Whether the library could check every rule in the firing set.

Chapter 1. Overview

The admin API manages flows, groups, rules and catalog fields at runtime. Every write takes effect immediately; no restart or redeploy is needed.

1.1. Base path and format

  • All endpoints are served by the business microservice itself, under /admin. Examples use http://localhost:8080.
  • Request and response bodies are JSON. Send Content-Type: application/json with every body.
  • Ids are numbers generated by the database. Codes (flowCode, groupCode) are strings you choose.

1.2. Enabling and securing the API

The API is on by default. Switch it off in a service that should not expose it:

yamlapplication.yml
rule-engine:
  admin:
    enabled: false
!
Warning

The library adds no authentication of its own. Expose /admin/** only to administrators: protect it at the API gateway or with the service's Spring Security configuration, and never publish it to the internet.

1.3. Status codes
