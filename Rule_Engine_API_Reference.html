Chapter 1. Overview

The admin API manages flows, groups, rules and catalog fields at runtime. Every write takes effect immediately; no restart or redeploy is needed.

1.1. Base path and format

  • All endpoints are served by the business microservice itself, under /admin. Examples use http://localhost:8080.
  • Request and response bodies are JSON. Send Content-Type: application/json with every body.
  • Ids are numbers generated by the database. Codes (flowCode, groupCode) are strings you choose.

1.2. Enabling and securing the API

The API is on by default. Switch it off in a service that should not expose it:

yamlapplication.yml
rule-engine:
  admin:
    enabled: false
!
Warning

The library adds no authentication of its own. Expose /admin/** only to administrators: protect it at the API gateway or with the service's Spring Security configuration, and never publish it to the internet.

1.3. Status codes

Table 1.1. Status codes used by the admin API

CodeMeaningTypical cause
200OKRead or write succeeded; body holds the result.
204No ContentDelete succeeded.
400Bad RequestValidation failed, unknown id or code, duplicate name, or a rule that does not compile.
409ConflictDeleting a flow or group that still has children, without force=true.
i
Note

An unknown id or code returns 400, not 404. Read the message field for the reason.

1.4. Error responses

Every 4xx response has the same body. Validation errors add fieldErrors.

json400 Bad Request — rule does not compile
{
  "timestamp": "2026-10-16T09:12:44.213Z",
  "status": 400,
  "error": "Bad Request",
  "message": "DRL compilation failed: [Message [id=1, level=ERROR, ... unable to resolve method using strict-mode: ValidationContext.getUserLimitt()]]"
}
json400 Bad Request — validation
{
  "timestamp": "2026-10-16T09:13:02.007Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "fieldErrors": { "factType": "must not be blank" }
}
